# Independent game authoring: decisions and experiment evidence

Status: accepted **sole Neon Harvest slice**, following the initial experiments, input/settling/tool isolation, and three-game live integration. Current automated validation passes **202 tests**, typecheck, lint and production build (2026-09-28); the local desktop browser/HTTP gate is now closed and the physical-device gate remains open. Read the [baseline/ownership map](BASELINE.md), [author walkthrough](AUTHORING.md), and [validation ledger](../VALIDATION.md). Historical passes are not current-run acceptance.

## Current decisions

**Simple game and source provenance.** Question → restore the expanded archived game or reconstruct the earlier simple design? Options → keep the later combat expansion, require an intact earlier implementation, or reconstruct from surviving references. Proposed decision → accepted by the user: reconstruct simple Neon Harvest from earlier types blob `11cfce70`, app blob `670a151b`, and complete later stash `2895d40^3`; an intact early rules/renderer source was not recovered. Evidence needed → deterministic rules tests and browser comparison with the accepted design. Owner → game owner/integration engineer. Dependencies → recovered reference material and public author contracts. Acceptance check → 45 seconds, 1–8 players, one `standard` mode, collection/chains/mines/pulse; no enemies, autofire, powers, sectors, core or combat metrics. Deferred scope → recovering exact old visuals/implementation or adding new game systems.

**One production game, one author boundary.** Question → keep three old examples/adapters in production or retire them now? Options → parallel paths, incremental legacy-game extraction, or one clean descriptor. Proposed decision → accepted: Neon Harvest is the only catalog entry; remove Lab/Tilt/Target code, `PartyGame`, shared game-specific state/interpolation/manifests and obsolete game forwards. Evidence needed → sole-entry catalog/bundle assertions, absence/import checks, generic fixture tests and live play. Owner → implementing engineer. Dependencies → generic runner, snapshots, screen and ledger already proven by the prior slice. Acceptance check → only the game folder and catalog registration supply game-specific integration; cross-game policy coverage uses test-only descriptors; old pause/substitution policies are explicitly retired. Deferred scope → another production game, separate packages, remote bundles and wholesale directory moves.

**Reusable absolute touch aim.** Question → how can a player aim, lift, then pulse without moving to center? Options → spring-return stick, game-specific phone code or a reusable absolute pad. Proposed decision → accepted: `aim-pad` maps its rectangle to signed square coordinates, starts centered, retains the last accepted value on release/cancel/lost capture/unmount, and emits no activation. `aim-and-pulse` composes named `aim` and `pulse` controls; motion pointer uses the same semantic aim. Evidence needed → corners, square bounds, rotation, keyboard/mouse/touch, independent button, retired callbacks and normalized primary-frame conversion. Owner → controller/runtime owners. Dependencies → capture kit, generation-bound `ControlPort`, registry validators and existing resolver. Acceptance check → the pad appears automatically in designer/gallery/preview; holding or lifting never pulses; suspension still clears runtime input. Deferred scope → binary expansion, sensor-provider redesign and more than four discrete slots.

**Bounded deterministic gameplay.** Question → how much of the recovered design belongs in this slice? Options → expand game systems or implement the accepted simple rules. Proposed decision → seeded waves and analytic motion; sparks 10, gold 30, multiplier `min(5, 1 + floor(chain / 5))`, chain reset after a gap greater than 2400 ms, and double pickup points in the last 10 seconds. Mines warm for 1100 ms, cost up to 50, reset chain and stun for 1000 ms. Pulse radius is 170 logical pixels with a six-second edge-only cooldown. Evidence needed → swept pickup, nearest-player claims, exact ties rotated by node ID/fixed roster, cooldown/stun/bonus boundaries and deterministic replay. Owner → game owner. Dependencies → semantic input, authoritative time and fixed eligibility. Acceptance check → at most 70 nodes/96 effects, game-local `collected`/`bestChain`/`mineHits` statistics, cloneable bounded state. Deferred scope → enemies, powers, combat and additional modes.

**Cutoff and awards.** Question → complete immediately, replay the world for late actions, or retain bounded settling? Options → immediate completion, rollback, fixed final drain. Proposed decision → preserve framework-owned 200 ms maturity/settling. Continuous collection and spawning stop at cutoff; only terminal pulses drain during settling, using action-time cooldown/stun/bonus without rolling back collections. Every action timestamp is in `[startAt, endAt)` and receipt is strictly before `endAt + 200`. Evidence needed → exact boundaries, reversed arrivals, disconnect races, abort and duplicate completion. Owner → engine/game/session owners. Dependencies → shared arbitration and valid final snapshots/outcomes. Acceptance check → finalize once; each eligible opponent placed below yields one session point, ties share awards, disconnected outcomes persist and abort awards nothing. Deferred scope → rollback, adaptive deadlines, teams, intermediate awards, persistence and host migration.

**Presentation and reports.** Question → expose authority to renderers or use the existing immutable sampled boundary? Options → mutable live reads or read-only presentation with separate report hydration. Proposed decision → retain a single sampled frame per draw, optional read-only local cursors/reduced-motion preference, game-owned interpolation and local renderer failure isolation. Results/awards use sampled progress; complete ledger totals can fill current-roster standings only at a revision no newer than the sampled one. Evidence needed → delayed host/remote parity, known successful-draw marker ACKs, explicit event clocks, no hydration audio replay, unsupported/recovery behavior and report retention. Owner → screen/runtime/session owners. Dependencies → generic envelope and revisioned progress. Acceptance check → renderer cannot award, malformed snapshots preserve the last good frame, reconnect can reissue lost resync, old rounds cannot replay cues, host loss preserves completed reports. Deferred scope → general audio assets, non-Canvas renderers and process sandboxing.

**Compatibility and distribution.** Question → permit mixed participants after adding the control/removing old games? Options → negotiate mixed versions or require one synchronized upgrade. Proposed decision → application protocol **4** for signaling join/welcome across all roles; reject missing/mismatched versions before admission/peer setup and stop retry loops. Keep the existing binary frame and resolved controller schema. Preserve calibration, diagnostics and reports in production; keep gallery/designer/preview/Motion Lab/harness development-only. Evidence needed → version rejection, retained control assets, sole-game bundle checks, development/production route tests. Owner → runtime/backend/tooling owners. Dependencies → current scaffold and strict production graph assertion. Acceptance check → update frontend/signaling together and reload all phones/screens; no tool implementation/style leaks and no deleted game imports. Deferred scope → mixed-version mode, hosting changes and dependency upgrades. Rollback → restore matching frontend/signaling together and start fresh rooms.

## Historical experiments and failures

The original four investigations used 4h/4h/3h/3h caps in one session; scaffolding overlapped and no separate elapsed-time measurement was claimed. Their game implementations were later migrated or retired. Preserve the observations, not a second production path.

| Stage / question                                                 | Evidence and limitation at that stage                                                                                                                                                                                                                                                                                                                            |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Can an existing game run without shell/network ownership?     | A Tilt Rally adapter wrapped `PartyGame` and the old renderer behind the harness. Both displays used production snapshot encoding/timeline, including delay. Temporary legacy state/interpolation and a second lifecycle clock were identified; the follow-up moved lifecycle to the shared runner. Those game adapters are now retired by the current decision. |
| 2. Can a new game own unknown state?                             | Target Practice owned `{ targets, hits, shots, nextSpawnAt }`, used aim-and-fire, and joined through its folder/catalog. Load/readiness/binding failures, immutable presentation and renderer isolation were tested. Its role was architectural evidence, not a permanent required game.                                                                         |
| 3. Does a working control preview prove transport safety?        | A four-control fixture proved two independent vectors and separate fire/cancel actions through the existing port. It did **not** prove transport correctness: a stale obsolete-generation generic value was accepted initially. Generation/sequence/time/shape validation and atomic activation payloads replaced that characterization with rejection tests.    |
| 4. Can different raw scores safely contribute to session points? | Tilt Rally and Target Practice proved placement-based awards, rematches, ties, duplicate/conflicting completion, fixed eligibility and aborts. Placements `1,1,3,4` gave `2,2,1,0`. Current cross-game regressions use test-only descriptors.                                                                                                                    |
| Live catalog and reports                                         | The three-game catalog and one runner replaced opt-in paths. A realistic fifty-round/eight-player report exceeded the relay limit, so history became atomic bounded reliable batches. Congestion then required bounded queued delivery rather than dropping remaining chunks.                                                                                    |
| Live review repairs                                              | Lost reconnect resync, disappearing nonparticipant totals, and cursor decoration exceeding a final snapshot budget were found and repaired with regressions. Cursor space is reserved before awards and the validated final envelope is retained.                                                                                                                |

Preserved contracts: values capture generation, per-action sequence, source time and a detached validated payload before throttling. Held values retain source time plus optional observation time. Value-bearing activations carry their own immutable value; press-only controls retain binary recovery. Ports retire on reconfiguration, suspension and close. These remain shared guarantees after the former games are removed.

Reports retain all-participant totals and the latest 50 records. Outcome statistics are bounded to 16 finite numeric keys, 64 characters per key and 1 KiB UTF-8 JSON. Hydration messages stay below 48 KiB including routing wrappers, assembly is capped at 4 MiB, and the reliable pending history queue is bounded to 64 MiB with revision coalescing and 50 ms retry. Configuration and events bypass that history queue. These are bounded in-memory reports, not persistence.

**Review repair: immediate cursor admission.** Question → can the immediate display path trust any decoded local packet? **Review repair: snapshot size.** Question → do node/effect counts alone bound a full round envelope? Options → reduce gameplay, broaden the wire limit, or remove unused repeated sound identity. Proposed decision → omit optional player IDs from Neon hit-audio events; retain bounded effects, outcomes and report attribution. Evidence needed → a full shared-runner round with eight maximum-length IDs and rotated event history. Owner → game/integration engineer. Dependencies → existing final-state validation and 47 KiB envelope limit. Acceptance check → 345 hit events over 45 seconds, 66 peak nodes, 22 peak effects, and a 29,938-byte peak encoded envelope; one accepted completion. The original stress case failed before this repair. Deferred scope → changing generic byte limits or audio assets.
