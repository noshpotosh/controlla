## Current scope and provenance

Neon Harvest is a 45-second, 1–8-player game with one `standard` mode. Players move to collect sparks/gold, avoid warming mines, and press a separate pulse action. Its game-local state, rules, renderer, metadata and tests belong in `src/client/minigames/neon-harvest/`; the production catalog registers it once. Host and harness use the same `RoundRunner` and validated snapshots.

This is a reconstruction of the earlier simple game. The intact earlier rules/renderer were not recovered: the reference set includes earlier type blob `11cfce70`, app blob `670a151b`, and later complete stash `2895d40^3`. The user accepted reconstructing the simple design from those sources. The later combat expansion is excluded: no enemies, autofire, powers, sectors, core or combat statistics. Preserve this provenance when evaluating visual or behavioral parity; a byte-for-byte restoration is not claimed.

Latency Lab, Tilt Rally, Target Practice, `PartyGame`, their combined `GameState`, game-specific legacy interpolation, legacy manifests and compatibility game forwards are retired from the production path. Pause/substitution policies that served only those old games are retired too. Cross-game ledger/lifecycle properties remain covered by small test-only descriptors; retaining an obsolete production game is not their test strategy. Reusable controls/layouts, calibration, diagnostics, reports, and the development-only Motion Lab remain.

Core now retains only `pointer.ts`, `calibration.ts`, `motion/trace.ts` and `types.ts` (`Point`, `Quaternion`, `clamp`). The engine migration removed old module paths and moved engine type exports without forwards. Its dependency guards preserve the existing type-only `IconName` vocabulary while excluding icon UI from execution.

The shell contracts in `shell/ports.ts` expose safe identity, UI state, typed diagnostics and explicit room/host/phone commands. The adapter caches detached frozen projections, preserves command and screen-port identities, and retires subscriptions and captured control ports on close. `GameCanvas` alone samples presentation frames; `RoomScreen` receives it as an injected slot. Import checks include transitive type edges, re-exports, aliases and dynamic imports, with explicit composition/adapter exceptions. Old UI paths have no forwarding modules.

The controls boundary is now explicit:

- `src/client/controls/api.ts` owns dependency-free controller requirements/specifications, capabilities, layouts, configuration, control definitions/ports and output types. The game API reexports the author-facing controller requirements and output types.
- `src/client/controls/resolve.ts` owns layout selection, capability fallback, binding validation and resolved transport-capacity checks. `controllerSpec(descriptor)` in the engine supplies only identity and controller requirements.
- `src/client/controls/types.ts` retains UI view props. Control views may use React, the capture kit and the type-only `IconName` vocabulary; resolver/registry runtime dependencies remain React-free.
- `Manifest`, `src/core/config.ts`, `controllerManifest`, moved contract reexports and the experimental controller resolver forwards are removed, with no controller compatibility aliases. Core sensor behavior, runtime callbacks and calibration remain in their existing owners.
- `scripts/new-control.ts` registers types in the controls API and uses an explicit stylesheet marker; generation and copying are tested in temporary fixtures and never write core types. A real built-in `--from stick` check exposed shared-type renaming; the repaired generator now passes actual stick/dpad copy and typecheck regressions.

Browser tools now live in `src/client/devtools/`, including the game harness. Its former general API/screen/session/catalog forwarding modules are removed; tests and fixtures import production owners directly. Reusable controls are in `src/client/controls/`, with saved layouts in `layouts/`. Runtime motion sampling and shared trace types retain their owners. Production source graphs (including type edges) and bundle/CSS checks exclude the entire tool domain.

## Decisions and preservation requirements

**One authoring path.** Question → how should the next game prove independence? Options → retain old adapters, add another special case, or exercise a single descriptor through both harness and live rooms. Proposed decision → accepted: one Neon Harvest folder plus one catalog entry; remove the old game-specific compatibility path. Evidence needed → import enforcement, headless and delayed-display play, live role routing. Owner → implementing engineer/game owner. Dependencies → public contracts and shared runner. Acceptance check → no Neon Harvest branch in shell, screen or authority; game state stays out of shared types. Deferred scope → separate packages, remote loading, public SDK and broad directory relocation.

**Reusable absolute aim.** Question → how does touch retain a chosen aim while a separate button pulses? Options → spring-centered stick, bespoke phone UI, or a reusable absolute pad. Proposed decision → accepted: `aim-pad` emits a signed square vector, holds the last accepted position on release/cancel, and emits no activation; named `aim` and `pulse` controls compose `aim-and-pulse`. Evidence needed → corners/rotation, keyboard and pointer release/cancel, independent button, stale-port and normalized-pointer integration. Owner → controller/runtime owners. Dependencies → existing `ControlPort`, capture kit and resolver. Acceptance check → no center jump on release and no obsolete callback relabels input. Deferred scope → new binary layouts and more than four discrete slots.

**Preserve framework behavior, retire unused game policy.** Question → which old behavior still belongs to the product? Options → carry combined games indefinitely or retain only shared guarantees and the accepted freeze policy. Proposed decision → keep host authority, rooms/resume, ACK/generation/time/sequence checks, fixed eligibility, 200 ms settling, immutable presentation, reports and bundle isolation; retire old pause/substitution gameplay. Evidence needed → meaningful migrated regression tests and fault walkthroughs. Owner → integration engineer. Dependencies → current sole-game rules and generic test fixtures. Acceptance check → abort awards nothing, repeated completion cannot duplicate awards, host loss preserves completed reports, and local cursors remain immediate. Deferred scope → new disconnect policies, host migration and persistence.

**Controller ownership and capacity.** Question → should controllers depend on game metadata and core configuration? Options → preserve the bridge, rename it, or own a pure contract and validated resolver. Proposed decision → implemented: dependency-free controls API, `ControllerSpec` projection and one resolver; no moved aliases. Evidence needed → committed contract/resolver stages, import graph and CLI fixtures, preserved input/calibration tests, and post-migration browser flow. Owner → controller/integration engineer. Dependencies → completed Neon baseline `2692738`; contracts `b9a0808`; resolver `2a6322c`. Acceptance check → 224 integrated tests and typecheck/project-lint/build checks pass; at most one resolved pointer/tilt action and four press slots; two independent generic touch vectors remain supported. Raw resolution now applies layout validation already applied by the former engine adapter, so rejecting unimplemented legacy widgets is not a new production restriction. Deferred scope → sensor-provider lifecycle, binary expansion, broad relocation, additional games and deployment.

No phone, camera, physical latency, TV, TURN or cross-household acceptance follows from these architecture checks. Keep the [validation ledger](../VALIDATION.md) authoritative.
